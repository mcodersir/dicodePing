# dicodePing v1.9.0-rc.10

> Android startup and scanner hotfix: bounded splash preparation, 30% per-source startup sampling, lifecycle-safe foreground scanning, tabbed highlighted logs, and strict bundled-core inventory checks.

## فارسی

RC10 روی بازسازی کامل اسکنر تمرکز دارد. مسیر دریافت کانفیگ در دسکتاپ و Android با الگوریتم مرحلهٔ اول پروژه DicodeConfigChecker هم‌راستا شده است: ابتدا VPN داخلی dicodePing واقعاً متصل و تأیید می‌شود، مسیر Telegram پیش‌سنجی می‌شود، `t.me/s/<channel>` و سپس `telegram.me/s/<channel>` خوانده می‌شوند، کانفیگ‌های خام پیش از قطع VPN ذخیره می‌شوند و بعد از قطع کامل VPN، تست واقعی Xray انجام می‌شود.

| بخش | تغییر |
|---|---|
| وضعیت اتصال اسکنر | دکمه پس از اتصال دیگر روی «در حال اتصال» باقی نمی‌ماند و مرحلهٔ دریافت Telegram را نمایش می‌دهد. |
| مسیر Telegram در دسکتاپ | SOCKS5 داخلی و DNS راه‌دور در اولویت است؛ TUN/direct فقط fallback است. |
| الگوریتم دریافت | یک درخواست به `t.me` و در صورت شکست یک درخواست به `telegram.me`، سپس dedupe و انتخاب جدیدترین کانفیگ‌ها. |
| پیش‌سنجی | قبل از ساخت صدها Job، دسترسی واقعی Telegram از داخل VPN بررسی می‌شود و خطای مسیر سریع و شفاف نمایش داده می‌شود. |
| پایداری | timeout هر مسیر مستقل شده؛ خطای مستقیم دیگر فرصت fallback را مصرف نمی‌کند. |
| Android | concurrency به چهار درخواست محدود، حافظه پاسخ محدود، دریافت مرحله‌ای، لاگ جداگانه موفق/ناموفق و توقف ایمن سرویس. |
| خروجی | فقط یک منبع ثابت `SUB` جایگزین می‌شود. |

### مراحل اسکن

1. انتخاب و اتصال به سرور bootstrap سالم.
2. تأیید اتصال واقعی و مسیر Telegram.
3. دریافت از ۹ کانال رتبهٔ اول با سقف ۸ کانفیگ و ۳۱۵ کانال رتبهٔ دوم با سقف ۹ کانفیگ.
4. ذخیره اتمیک نامزدهای خام.
5. قطع کامل VPN داخلی.
6. اجرای تست واقعی Xray و درخواست HTTP برای هر نامزد.
7. جایگزینی منبع ثابت `SUB` با نتایج سالم.

### باگ‌فیکس Android همین بسته

- اسپلش با سقف زمانی مشخص، دریافت/نوسازی منابع، نمونه‌گیری دقیق ۳۰٪ از هر منبع، تست سریع و بررسی آپدیت را انجام می‌دهد و در خرابی شبکه با دادهٔ کش‌شده وارد برنامه می‌شود.
- کار سنگین اسکنر خارج از Thread رابط کاربری و داخل Foreground Service اجرا می‌شود؛ درخواست‌های HTTP قابل لغو و فراخوانی‌های JNI هستهٔ Xray سراسری و سریال هستند.
- لاگ زنده به دو تب «بررسی» و «خروجی» تقسیم شده و رخدادهای موفق، خطا و مراحل اتصال رنگ‌بندی می‌شوند.
- CI وجود Xray، Aether و Usque را برای `arm64-v8a` و `x86_64` در APK نهایی بررسی می‌کند و در صورت نبود یا ناقص‌بودن هر هسته Build را متوقف می‌کند. حجم APK به‌صورت مصنوعی افزایش داده نمی‌شود؛ موجودی و اندازهٔ واقعی هسته‌ها گزارش می‌شود.

## English

RC10 rebuilds the scanner path across desktop and Android. The collection stage now follows the DicodeConfigChecker channel algorithm: dicodePing first establishes and verifies its own bootstrap VPN, validates the Telegram route, requests `t.me/s/<channel>` with a single `telegram.me/s/<channel>` fallback, atomically stores raw candidates, fully disconnects the bootstrap VPN and only then runs isolated real Xray HTTP probes.

| Area | Change |
|---|---|
| Scanner connection state | The primary action no longer remains stuck on “Connecting”; it immediately advances to Telegram collection after verification. |
| Desktop Telegram route | The app-owned SOCKS5 listener with remote DNS is preferred; TUN/direct is retained as fallback. |
| Collector algorithm | One primary-host request, one mirror fallback, newest-first extraction and deterministic deduplication. |
| Route preflight | Telegram reachability is verified before hundreds of channel tasks are created. |
| Reliability | Each route has an independent timeout budget, so a failed direct route cannot consume the SOCKS fallback budget. |
| Android | Four-request concurrency cap, bounded response memory, per-channel success/error logs and lifecycle-safe foreground scanning. |
| Persistence | Every run atomically replaces the single `SUB` source. |

### Android hotfix in this package

- Startup now has a hard time budget while refreshing sources, sampling exactly 30% per source, running quick probes and checking for updates; network failure opens the UI with cached data instead of trapping the user on the splash screen.
- Scanner work runs outside the UI thread in a foreground service; HTTP calls are cancellable and process-wide Xray JNI operations are serialized.
- Live scanner logs are split into highlighted Review and Output tabs.
- CI verifies Xray, Aether and Usque for both `arm64-v8a` and `x86_64` inside the final APK and fails on a missing or incomplete core. APK size is not padded artificially; the real native payload is reported.
