# dicodePing 1.8.0 RC1

This prerelease turns the previously decorative connection switches into
capability-checked runtime features across Windows, Linux, and Android.

## Connection cores

- Xray remains the built-in default and the only core present in the base app.
- Aether 1.4.0 is downloaded on demand on Windows/Linux with its published
  SHA-256, started in MASQUE + Ironclad + quick-reconnect mode, and accepted
  only after a real HTTP request succeeds through its SOCKS tunnel.
- Psiphon is downloaded on demand with an immutable URL and SHA-256. Desktop
  use requires an authorized signed `client.config`; Android downloads and
  installs the verified ShirOKhorshid companion APK.
- Android caches and verifies the official Aether Termux archive separately
  from the APK. Termux is required because modern Android prohibits an app
  from executing newly downloaded native code from its writable directory.
- Core installation uses bounded downloads, traversal-safe extraction,
  per-core locks, atomic directory replacement, and executable re-verification.
- Exactly one core is active. Selecting an alternative core dims and disables
  Servers and Scanner; Splash also skips the Xray subscription pipeline.

## Scanner and CDN

- Scanner connects through the best primary Xray server, crawls Telegram
  channels, disconnects the bootstrap tunnel, then performs native real-HTTP
  Xray probes on the discovered configs.
- A user-selected subscription name is preserved, sanitized, persisted as a
  real source, shown on Servers, and its configs can be copied from Scanner.
- CDN formatting supports VMess, VLESS, Trojan, and Shadowsocks endpoints. It
  replaces the dial address while retaining the origin as TLS SNI and WS Host.

## VPN sharing and per-app VPN

- Windows sharing uses the `HNetCfg.HNetShare` ICS COM API and restores only
  the connections changed by dicodePing.
- Linux sharing configures `hostapd`, `dnsmasq`, IP forwarding, conntrack-aware
  forwarding and NAT rules, with rollback on partial failure and exact cleanup.
- Android sharing uses a dedicated root/system path that routes marked
  USB/hotspot traffic into the live VPN TUN. Stock unprivileged Android reports
  the missing capability instead of a false success.
- Android Per-app VPN is wired end-to-end: disabled, allowlist, and denylist
  modes call `addAllowedApplication` / `addDisallowedApplication` before the
  TUN is established.

## Stability and resource improvements

1. Core processes have one owner and are terminated and waited on during every
   switch/disconnect, preventing orphan background tasks.
2. Download files, extraction directories, and failed installs are cleaned up
   deterministically; corrupt or partial cores never become active.
3. System proxy and IP-forwarding state are recorded and restored on normal
   stop, startup failure, and process exit.
4. Core selection and installation are atomic and locked, preventing concurrent
   UI clicks from racing or producing mixed installations.
5. Android VPN start generations cancel and join superseded jobs, while its
   SupervisorJob, metrics loop, network callback, TUN descriptor, native core,
   and sharing rules are all released from one lifecycle path.
6. Scanner and connection concurrency, network buffers, retry workers, DNS
   workers, and crawl workers are selected from detected CPU and memory.
7. Real connection validation rejects a merely running process: Xray, Aether,
   and scanner candidates must carry actual HTTP traffic before success.

- Android XML/resource/project validator.
- Windows packaged startup discovery smoke test.
- Linux offscreen packaged startup discovery smoke test.
