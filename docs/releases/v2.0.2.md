# dicodePing v2.0.2 — انتشار پایدار

این نسخه یک اصلاح اساسی روی همزمانی واقعی اسکنر اندروید است. نسخه قبلی (v2.0.1)
سعی کرد همزمانی پروب‌های Xray را با `SCANNER_PROBE_CONCURRENCY = 3` افزایش دهد، اما
به‌دلیل قفل process-wide کتابخانه `libv2ray`، همه پروب‌های Xray HTTP عملاً ترتیبی
اجرا می‌شدند و کاربر هیچ بهبودی حس نمی‌کرد. v2.0.2 این مشکل را با یک معماری دو‌فازی
حل می‌کند که همزمانی واقعی را روی اندروید ممکن می‌سازد و همچنین README کاملاً
حرفه‌ای جایگزین README قبلی می‌شود.

## همزمانی واقعی اسکنر اندروید

### مشکل ریشه‌ای

کتابخانه `AndroidLibXrayLite` (نسخه 26.7.11) یک کلاس Go singleton دارد که در فضای
پروسه اجرا می‌شود. متد `measureOutboundDelay` که در `CoreBridge.kt` فراخوانی می‌شود،
با `synchronized(OUTBOUND_PROBE_LOCK)` سری‌سازی شده است تا از race condition داخل
`libgojni` جلوگیری کند. این یعنی صرف‌نظر از تعداد coroutineهایی که روی
`Dispatchers.IO` اجرا می‌شوند، در هر لحظه فقط یک پروب Xray HTTP فعال است.

نسخه v2.0.1 تلاش کرد با `SCANNER_PROBE_CONCURRENCY = 3` و یک حلقه `chunked(6)` سه
پروب موازی اجرا کند، اما چون همه روی همان قفل `OUTBOUND_PROBE_LOCK` مسابقه
می‌کردند، عملاً هیچ بهبودی حاصل نشد.

### راه‌حل دو‌فازی v2.0.2

اسکنر اندروید حالا به دو فاز تقسیم شده:

**فاز A — پروب موازی TCP handshake delay**
- ۱۲ سوکت همزمان روی `Dispatchers.IO` با `Semaphore(SCANNER_TCP_PROBE_CONCURRENCY = 12)` اجرا می‌شوند.
- هر سوکت یک نمونه مستقل `java.net.Socket` است — هیچ JNI state مشترکی وجود ندارد.
- برای هر کاندید، تاخیر TCP handshake اندازه‌گیری می‌شود.
- کاندیدهای مرده (که handshake ناموفق بود) فیلتر می‌شوند.

**فاز B — پروب سری Xray HTTP روی برترین بازماندگان**
- کاندیدهای زنده بر اساس تاخیر TCP مرتب می‌شوند.
- فقط `SCANNER_NATIVE_CANDIDATE_LIMIT` (۹۶) کاندید برتر از طریق هسته Xray تست می‌شوند.
- چون فاز A میزبان‌های مرده را از قبل فیلتر کرده، فاز B فقط روی ۲۰-۳۰ کاندید زنده اجرا می‌شود (به جای ۴۰-۶۰ کاندید در نسخه قبلی).
- حلقه فاز B سری است، اما چون ورودی کوچک‌تر است، زمان کل به‌شدت کاهش می‌یابد.

### اثر خالص

روی یک اسکن ۴۰ کاندیدی:
- **فاز A**: حدود ۳-۵ ثانیه (موازی با ۱۲ سوکت)
- **فاز B**: حدود ۸-۱۵ ثانیه (سری اما فقط روی ۲۰-۳۰ کاندید زنده)
- **مجموع**: ۱۵-۲۰ ثانیه

در نسخه‌های v2.0.0 و v2.0.1 همان اسکن ۶۰-۹۰ ثانیه طول می‌کشید چون همه ۴۰ کاندید به‌صورت ترتیبی از طریق قفل JNI تست می‌شدند.

همین معماری دو‌فازی برای `enrichScannerRecords` (محاسبه پینگ/لوکیشن پس از ذخیره) هم اعمال شده، پس مودال «محاسبه پینگ و لوکیشن؟» هم حالا واقعاً سریع است.

## بهبود همزمانی دسکتاپ

دسکتاپ از قبل با `ThreadPoolExecutor` و تا ۲۸ worker موازی کار می‌کرد (هر پروب یک
فرآیند `xray` مستقل است که از طریق یک پورت محلی تست می‌شود). اما صف پروب با
`SCAN_PROBE_QUEUE_LIMIT = min(72, ...)` محدود شده بود که در اسکن‌های سنگین باعث
می‌شد workerها نخست از صف خالی شود و ظرفیت ۲۸-worker کامل استفاده نشود.

v2.0.2 این سقف را به `min(120, max(SCAN_PROBE_WORKERS * 4, ...))` افزایش داد تا
workerها در طول اسکن کاملاً اشغال بمانند. این کار به‌خصوص روی macOS و Windows
(که startup overhead فرآیند xray بالاتر است) محسوس است.

- `versionCode` اندروید از ۵۷ به ۵۸ افزایش یافت.
- `RELEASE_VERSION` از `2.0.1` به `2.0.2` در همه بیلدرها و فایل‌های متادیتا.

- `dicodePing_android/build_apk.sh` و `build_apk.bat`: `VERSION` به `2.0.2` به‌روزرسانی شد (مشکل v2.0.1 که باعث شکست بیلد شد دیگر تکرار نمی‌شود).
